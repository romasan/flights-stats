# Статистика рейсов аэропортов

Node.js-сервер и веб-приложение для сбора и визуализации статистики рейсов аэропортов. Сейчас поддерживаются семь аэропортов — Пулково (LED), Уфа (UFA), Толмачёво (OVB), Шереметьево (SVO), Внуково (VKO), Домодедово (DME) и Сочи (AER), архитектура позволяет легко добавить другие.

## Структура проекта

## Как это работает

### 1. Сбор данных (`server/scheduler.js` + `server/fetcher.js`)

Сервер сам планирует и выполняет сбор данных — отдельный cron не нужен. У каждого аэропорта (юнита в `server/units/*`) своё расписание и ретраи:

- **Пулково (LED)** — ежедневный сбор: в заданный час (по умолчанию 01:00 по времени сервера, `FETCH_HOUR`) запрашиваются данные за вчера. При ошибке — ретрай через 1 час (`FETCH_RETRY_DELAY_MS`), всего до 4 попыток (`FETCH_MAX_ATTEMPTS`, т.е. 1 попытка + 3 ретрая). Если данные за вчера уже успешно загружены — повторная загрузка не выполняется.
- **Уфа (UFA)** — интервальный сбор: каждый час (`intervalMs`, по умолчанию 1 ч) запрашиваются рейсы за текущий день (дата «сегодня» считается по времени Уфы, `Asia/Yekaterinburg`, UTC+5) и обновляются их статусы. Ретраев нет (`maxAttempts: 1`), т.к. опрос и так происходит каждый час. Новые рейсы добавляются, а уже виденные обновляются по статусу/времени без удаления (режим `merge`), чтобы к концу дня не «терять» уже вылетевшие/прилетевшие рейсы. Статусы рейсов Уфы ещё на этапе парсинга приводятся к каноническому виду (Отправлен/Прибыл, Задержан, Отмена, Без статуса) — тому же, что у Пулково, — а исходный текст статуса с сайта сохраняется отдельно (см. ниже, колонка `status_raw`, и попап со списком рейсов).
- **Толмачёво (OVB)** — ежедневный сбор данных за вчера, как у LED; дата «вчера» считается по времени Новосибирска (`Asia/Novosibirsk`, UTC+7). Ответы сайта защищены простым JS-челленджем (куки `__jhash_` и т.п.), поэтому юнит загружает табло через headless-Chromium (`playwright-core`): открывает страницу расписания, дожидается прохождения челленджа и POST-ом к `/ajax/ttable.php` снимает HTML-табло за `day=yesterday`. Ответ содержит вылеты и прилёты вместе — направление определяется по маршруту в карточке (`Новосибирск → Город` / `Город → Новосибирск`). Статусы приводятся к каноническому виду, время — локальное новосибирское.
- **Шереметьево (SVO)** — ежедневный сбор данных за вчера, как у LED; дата «вчера» считается по московскому времени (`Europe/Moscow`, UTC+3). В отличие от «живого» табло, сайт svo.aero (SPA) отдаёт рейсы произвольного диапазона дат через публичный JSON-API без авторизации: `GET /bitrix/timetable/?direction=arrival|departure&dateStart=…&dateEnd=…` (дата в ISO с `+03:00`, `perPage=9999`). Запрос за сутки возвращает весь день целиком (вылеты и прилёты запрашиваются отдельно). План — поле `t_st`, факт — `t_otpr` (вылет) / `t_at` (прилёт). Статусы SVO «сворачиваются» в итоговый текст (у вылета даже «Прибыл в <город> …»), поэтому канонический статус определяем по фактическому времени (выполнен → Отправлен/Прибыл), а отмены — по слову «отмен…»; «Задержан» фронтенд вычисляет сам из факта/плана.
- **Внуково (VKO)** — ежедневный сбор данных за вчера, как у LED; дата «вчера» считается по московскому времени (`Europe/Moscow`, UTC+3). Табло vnukovo.ru — «живая» лента (Vue-SPA), защищённая JS-челленджем, а данные `/rest/flights/online` приходят зашифрованными и расшифровываются в браузере; поэтому юнит, как и OVB, загружает табло через headless-Chromium (`playwright-core`) и снимает отрендеренный DOM, а чтобы собрать весь завершённый «вчерашний» день — много раз дожимает кнопку «Загрузить предыдущие рейсы», пока лента не пройдёт в позавчера. Юнит «best-effort»: VKO почти для всех уже выполненных рейсов показывает статус «Совершил посадку» **без фактического времени** (факт «Вылетел/Прилетел в ЧЧ:ММ» остаётся лишь у части), поэтому корректно считаются рейсы и отмены, а задержки — только у тех рейсов, где факт доступен. Направление задаётся отдельной страницей табло (`?bound=arrival|departure`); из прошедшей по дням ленты оставляем только рейсы целевого дня по его метке у рейса («8 сентября»).
- **Сочи (AER)** — интервальный сбор, как у Уфы и DME: каждый час (`intervalMs`) запрашиваются рейсы за текущий день (дата «сегодня» по Москве, `Europe/Moscow`, UTC+3). У aer.aero нет публичного API на произвольную дату — онлайн-табло `/flights/online-schedule/` (Bitrix) показывает только текущий операционный день целиком и отдаётся обычным GET сразу HTML-ом (без JS-челленджа). Раз в час юнит снимает табло и **накапливает** рейсы по `externalId` (режим `merge`), не удаляя уже виденные; строки вылетов и прилётов лежат на одной странице — нужное направление отбирается по классу карточки (`data-case-select="out|in"`, а также `main-widget-page--arrival`), а из ленты остаются только рейсы с плановым днём «сегодня» (чтобы на границе полночи не было дублей). План берётся из data-атрибутов строки (`data-time`/`data-time-minute`), фактическое время — только у выполненного рейса («Отправлен»/«Прибыл») из «актуальной» строки времени, где есть полная дата (иначе «актуальное» время у изменённых/завершающихся рейсов может оказаться лишь обновлённым планом). Статусы приводятся к каноническому виду, у незавершённых рейсов («Регистрация», «Идёт посадка», …) статус пустой. Как и DME, юнит работает на «живом» табло текущего дня и корректно собирает полноценные сутки только к их концу; фактический вылет рейсов, пересекающих полночь, учитывается в плановых сутках. Парсер проверен на реальном ответе сайта, полная валидация — по итогам живого дня сбора.

- **Домодедово (DME)** — интервальный сбор, как у Уфы: каждый час (`intervalMs`) запрашиваются рейсы за текущий день (дата «сегодня» по Москве, `Europe/Moscow`, UTC+3). У DME нет публичного API на произвольную дату — онлайн-табло dme.ru отдаёт только «живое» скользящее окно на ~2–3 часа вокруг текущего момента (обычный GET, HTML приходит сразу, без JS-челленджа; докрутка истории закрыта анти-бот защитой `wv-data`). Раз в час юнит снимает это окно и **накапливает** рейсы по `externalId` (режим `merge`), не удаляя уже виденные; из каждого снимка берутся только рейсы, чей плановый день = «сегодня» (чтобы на границе полночи не было дублей). К концу суток накопленный «сегодняшний» день становится цельным «вчерашним». Статусы приводятся к каноническому виду (отмены/задержки/«Рейс вылетел»/«Прибыл»), а у незавершённых рейсов («Регистрация», «Идет посадка», …) статус остаётся пустым. Дата рейса берётся по плановому времени, поэтому у редких рейсов, пересекающих полночь, фактический вылет учитывается в плановых сутках.

Общий порядок сбора для каждого юнита и обоих типов рейсов (`arrival`, `departure`):

1. При старте сервера для каждого юнита вычисляется время следующего запуска и выставляется `setTimeout`. Для daily-юнитов, собирающих данные за «вчера» (LED, OVB, SVO, VKO), при старте дополнительно проверяется, есть ли уже успешно загруженные данные за целевую «вчерашнюю» дату: если их нет (например, сервер простаивал в ночные часы) — сбор запускается сразу при старте, а затем сервер возвращается к обычному ежедневному расписанию.
2. Если после всех попыток данные получить не удалось — в таблицу `fetch_log` записывается ошибка (аналог прежней записи в `fetch_flights.log`); эта информация возвращается фронтенду через API и показывается как предупреждение.
3. Успешный ответ API сохраняется:
   - сырой JSON — в архив на диске: `data/raw/<CODE>/<год>/<type>-<YYYYMMDD>.json` (для отладки/повторного разбора в будущем);
   - распарсенные поля рейсов — в таблицу `flights` в SQLite (только то, что нужно для отображения — дата, номер рейса, статус, план/факт времени, аэропорт).

Данные о конкретном аэропорте описываются модулем в `server/units/`: там заданы расписание/ретраи, способ построения HTTP-запроса и парсинг ответа к единому нормализованному виду. Простые юниты (LED) задают `urls` и `parseFlight(raw, type)` (GET, ответ — массив). Юниты с другим форматом запроса/ответа (UFA) реализуют `buildRequest(type, fileDate)` и `parseFlights(raw, type, fileDate)` (POST с телом form-urlencoded и конкретной датой, ответ — JSON с HTML-карточками рейсов). Юниты, чей сайт требует браузера (OVB, VKO), реализуют `fetchRawHtml(type, fileDate)`, который через headless-Chromium снимает табло и возвращает «сырые» данные, а `parseFlights` приводит их к общему виду. Чтобы **добавить новый аэропорт**, нужно создать аналогичный модуль и зарегистрировать его в `server/units/index.js`; на фронтенде он автоматически появится в выпадающем списке (список аэропортов сервер отдаёт через `/api/units`).

### 2. API

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/units` | Список аэропортов: `[{ code, name }]` |
| GET | `/api/units/:code/flights` | Все данные для отображения по аэропорту одним запросом: `{ unit, generatedAt, departures[], arrivals[], fetchErrors[] }` |

Формат одного рейса в `departures`/`arrivals`:

```json
{
  "fileDate": "20260719",
  "flightNumber": "FV 6587",
  "status": "Отправлен",
  "plan": "2026-07-19T00:10:00.000",
  "actual": "2026-07-19T00:12:00.000",
  "eventDate": "2026-07-19",
  "airportCode": "SCW",
  "airportName": "Сыктывкар"
}
```

`fetchErrors` — список дней, за которые не удалось получить данные после всех попыток: `[{ date: "YYYYMMDD", types: ["arrival", "departure"] }]`.

Помимо API сервер раздаёт статику из `public/` и отдаёт `index.html` по адресам вида `/<код аэропорта>/` (`/ufa/`, `/ufa`, `/UFA/`) — это клиентский роутинг одностраничного приложения (см. раздел «Визуализация»). Для неизвестных кодов (например `/XYZ/`) возвращается 404. Пути `/api/*` обрабатываются отдельным роутером и SPA-роутингом не затрагиваются.

Ответ API отдаёт только то, что нужно для отображения (без лишних полей исходного API аэропорта) и сжимается (gzip через `compression`), что при пары месяцев данных даёт запрос в разы легче, чем скачивание всех исходных JSON-файлов.

### 3. Визуализация (`public/index.html`)

Одностраничное приложение на HTML/CSS/JS без сборки (рендеринг выполняется в рантайме в браузере). Использует библиотеки (подключаются через CDN jsDelivr):

- **Preact** — UI-фреймворк (реактивный рендеринг интерфейса);
- **htm** — JSX-подобный синтаксис через tagged templates (без компиляции);
- **Chart.js** — построение графиков;
- **chartjs-plugin-datalabels** — подписи значений на графиках;
- **chartjs-chart-matrix** — тепловые карты.

Интерфейс разбит на Preact-компоненты (`Header`, `UnitSelect`, `Loader`, `SummaryCards`, `LineChart`, `HeatmapChart`, `StatsTable`, `FlightsPopup`, `FetchErrors`, `Content`, `App`), а сами графики Chart.js обёрнуты в компоненты через хуки `useRef`/`useEffect`.

При загрузке страница:

1. **Получает список аэропортов** (`GET /api/units`) и показывает выпадающий список в шапке (сейчас — Пулково, Уфа, Толмачёво, Шереметьево, Внуково и Домодедово).
2. **Загружает все данные выбранного аэропорта** одним запросом (`GET /api/units/:code/flights`).
3. **Агрегирует данные**:
   - дата рейса берётся по фактическому времени (ATD для вылетов, ATA для прилётов), при отсутствии — по плановому (STD / STA) — это поле `eventDate`, уже вычислено на сервере;
   - каждый рейс относится к статусу: `Отправлен` / `Прибыл`, `Задержан`, `Отмена`, `Без статуса`. Нормализация к этому набору выполняется на сервере при парсинге (у Уфы — в `server/units/ufa.js`), а исходный текст статуса с сайта сохраняется в БД в колонке `status_raw`;
   - рейсы со статусом «Отправлен»/«Прибыл», фактически отправленные/прибывшие с задержкой от выбранного порога, показываются как «Задержан» (порог выбирается в выпадающем списке: 0 минут, 15 минут, 30 минут, 1 час, 2 часа, сутки, «не важно» — по умолчанию 1 час; при «не важно» статус остаётся как в данных, без учёта задержки).
4. **Строит визуализации**:
   - **Сводные карточки** — количество дней, общее число вылетов/прилётов, а также суммарное количество отменённых и задержанных рейсов (с учётом выбранного порога задержки) с долей от общего числа в процентах;
   - **Линейные графики** — количество рейсов по статусам по дням;
   - **Тепловые карты** — вероятность отмены или задержки вылета/прилёта по дню недели и часу суток. Статус (отмена/задержка) выбирается выпадающим списком между блоками графиков: для обеих метрик используется плановое время (STD/STA), при его отсутствии — фактическое (ATD/ATA), а количество таких рейсов показывается в блоке предупреждений; дни без данных исключены;
   - **Таблицы** — количество рейсов по дням и статусам с итогами по строкам и столбцам. Заголовки столбцов кликабельны (сортировка по возрастанию/убыванию), клик по дате открывает попап со списком всех рейсов за выбранный день (номер рейса, направление, плановое и фактическое время, статус — для Уфы в попапе показывается исходный статус с сайта, например «Вылетел» или «Задержка», при этом цвет и сортировка соответствуют канонической категории; направление выводится как «код · название» (например «SCW · Сыктывкар»), а если табло аэропорта не отдаёт IATA-код (Толмачёво, Сочи, Домодедово) — только название города; если дата планового времени отличается от даты фактического, перед временем серым показывается дата; задержка считается по фактической разнице с учётом дат (рейс, прибывший раньше плана, не считается задержанным), до 60 минут показывается в минутах, а крупные — в формате «N д N ч N мин»; внутри попапа также доступна сортировка по столбцам). Попап закрывается по крестику, клику вне окна или клавише Esc.
5. **Показывает статус загрузки** в строке состояния и предупреждения о днях, когда данные не удалось загрузить (из `fetchErrors`).
6. **Загружается автоматически** при открытии страницы и при смене аэропорта в выпадающем списке.
7. **Синхронизирует выбранный аэропорт с адресом страницы**: корень сайта показывает аэропорт по умолчанию (Пулково), а при выборе другого аэропорта адрес меняется на `/<код>/` (например `/ufa/`) через `history.pushState` — такую ссылку можно скопировать или сохранить в закладки. При открытии прямой ссылки вида `/ufa/` соответствующий аэропорт автоматически подставляется в селектор и загружается его статистика; кнопки браузера «назад/вперёд» переключают аэропорт (обрабатывается событие `popstate`). Название аэропорта выводится в заголовке вкладки браузера.

## Запуск

### Установка зависимостей

```bash
npm install
```

Сбор данных Толмачёво (OVB) использует headless-Chromium (пакет `playwright-core`). Браузеры Playwright не скачиваются самим `npm install` — их нужно поставить один раз:

```bash
npx playwright-core install chromium
```

(Бинарники кладутся в системный кэш Playwright — `~/Library/Caches/ms-playwright` на macOS.)

### Запуск сервера

Для локальной разработки:

```bash
npm run dev
```

Для запуска в фоне на сервере используется [pm2](https://pm2.io/) (устанавливается автоматически как devDependency при `npm install`):

```bash
npm start   # запустить под pm2 с именем процесса flights-stats и сохранить конфигурацию (pm2 save)
npm run stop   # остановить процесс flights-stats
npm run logs   # смотреть логи процесса flights-stats
```

Сервер поднимает HTTP на порту `3000` (можно изменить через переменную окружения `PORT`), раздаёт статику из `public/`, отдаёт приложение по корню `/` и по адресам вида `/<код аэропорта>/` (SPA-роутинг), отвечает на `/api/*` и запускает встроенный планировщик ежедневного сбора данных (сбор не требует cron — работает, пока запущен процесс сервера).

Переменные окружения можно задать как в самом окружении (системные значения имеют приоритет), так и в файле `.env` в корне проекта (загружается сервером через `dotenv`). Образец со всеми переменными — в `.env.example`.

Переменные окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `3000` | Порт HTTP-сервера |
| `PUBLIC_DIR` | `public` | Каталог со статикой, разрешается относительно корня проекта |
| `DATA_DIR` | `<project>/data` | Каталог для БД и архива сырых JSON |
| `DB_PATH` | `<DATA_DIR>/flights.db` | Путь к файлу SQLite |
| `FETCH_HOUR` | `1` | Час (0–23) ежедневного запуска сбора для daily-юнитов (LED); может переопределяться в конфиге юнита (`fetchHour`) |
| `FETCH_RETRY_DELAY_MS` | `3600000` (1 час) | Задержка между повторными попытками при ошибке (значение по умолчанию; может переопределяться в конфиге юнита — `retryDelayMs`) |
| `FETCH_MAX_ATTEMPTS` | `4` | Максимум попыток на один тип рейсов (1 + 3 ретрая; значение по умолчанию; может переопределяться в конфиге юнита — `maxAttempts`) |

Параметры расписания и ретраев задаются в конфиге юнита (`server/units/<code>.js`): `schedule` (`daily` | `interval`), `intervalMs`, `fetchHour`, `maxAttempts`, `retryDelayMs`, `dateMode` (`yesterday` | `today`), `timeZone`. Если они не заданы — используются глобальные значения из таблицы выше.

### Просмотр статистики

Откройте `http://localhost:3000/` (или адрес сервера) в браузере — корень показывает статистику аэропорта по умолчанию (Пулково). Для каждого аэропорта есть свой адрес вида `http://localhost:3000/ufa/`, который можно копировать и добавлять в закладки (коды аэропортов — те же, что в `server/units/`, например `led`, `ufa`, `ovb`, `svo`, `vko`, `dme`, `aer`).

### Nginx (reverse proxy)

Если сервер стоит за nginx, нужно проксировать на приложение как корень, так и пути вида `/<код>/` и `/api/`. `proxy_pass http://localhost:7006;` **без** завершающего слэша сохраняет исходный путь запроса (`/ufa/` → `/ufa/`), поэтому отдельные правила для маршрутов аэропортов не нужны:

```nginx
server {
	client_max_body_size 20M;
	listen 80;
	listen 443 ssl;
	server_name f.nbauer.ru;

	# REST API приложения
	location /api/ {
		proxy_pass http://localhost:7006;
		proxy_http_version 1.1;
		proxy_set_header Host $host;
		proxy_set_header X-Real-IP $remote_addr;
		proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
		proxy_set_header X-Forwarded-Proto $scheme;
	}

	# SPA: корень и маршруты вида /ufa/ (код аэропорта)
	location / {
		proxy_pass http://localhost:7006;
		proxy_http_version 1.1;
		proxy_set_header Upgrade $http_upgrade;
		proxy_set_header Connection 'upgrade';
		proxy_set_header Host $host;
		proxy_set_header X-Real-IP $remote_addr;
		proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
		proxy_set_header X-Forwarded-Proto $scheme;
		proxy_cache_bypass $http_upgrade;
	}

	ssl_certificate /etc/letsencrypt/live/f.nbauer.ru/fullchain.pem;
	ssl_certificate_key /etc/letsencrypt/live/f.nbauer.ru/privkey.pem;
}
```
